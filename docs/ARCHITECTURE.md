# Архитектура

## Поток данных
```
OSM (Overpass, плитками)                      сценарий (overrides + params)
        │                                              │
        ▼                                              ▼
 map-data/importer ──► snapshot.json.gz ──► map-data/compiler ──► network.json(.gz)
                                                 │  генератор допущений, provenance
                                                 ▼
                              sim-worker (Web Worker) ── sim-core: createSimulation(network, config)
                                    │  кадры (typed arrays, transferable, пинг-понг)  60 Гц
                                    │  метрики по сегментам                            1 Гц
                                    │  отчёт об узких местах                            раз в окно / по запросу
                                    ▼
                              apps/web: Three.js (полотно, машины, светофоры) + React (панели, сценарии, A/B)
```
Компиляция сети происходит в главном потоке (или в отдельном воркере, если станет медленно), симуляция
только в воркере. Приложение статическое: никаких серверов, вся работа в браузере.

## Пакеты и зависимости
`contracts` ← `map-data` ← (снимок) ; `contracts` ← `sim-core` ← `sim-worker` ← `web` ; `web` ← `map-data`
(для применения overrides в браузере). `sim-core` не зависит от `map-data`: он получает готовый `Network`.

## Сеть в рантайме (sim-core)
`Network` (JSON, удобен людям) при `createSimulation` превращается в плоские структуры:
- массивы узлов, линков, полос, коннекторов с целочисленными индексами; словари `id → index` только на входе/выходе;
- для каждой полосы: длина, `startS/endS`, разрешённые классы, список коннекторов на выходе, соседи слева/справа;
- для каждого коннектора: точки конфликта с индексами других коннекторов, приоритет, группа сигнала, зебры;
- сегменты метрик: полоса нарезана по `metrics.segmentLengthM`, порядок фиксирован (`SegmentDescriptor[]`).

## Машины: структура массивов (SoA)
Пул фиксированной ёмкости `demand.vehicleBudget`. На каждую машину: `laneIdx`, `s` (метры вдоль полосы или
коннектора), `v`, `a`, класс, длина, параметры водителя (желаемая скорость, T, s0, вежливость, критические зазоры),
маршрут (индекс в таблице маршрутов + позиция), флаги, причина (`cause`) и корневая причина (`rootCause`),
таймеры (перестроение, ожидание, стоянка на остановке). Свободные слоты в списке. Машина всегда «на полосе»
или «на коннекторе»; коннектор моделируется как короткая полоса.

Для каждой полосы поддерживается упорядоченный по `s` список машин (индексы), обновляемый при движении и
перестроениях: поиск лидера и последователя O(1).

## Порядок шага `step()` (dt = 0.1 с)
1. **Сигналы.** Контроллеры вычисляют состояние групп по времени и `offsetS` (см. ниже).
2. **Пешеходы.** Для каждой зебры: генерация приходов (пуассон по часу суток, только в зелёный для регулируемых),
   продвижение по зебре со скоростью `walkSpeedMps`, счётчик «на зебре».
3. **Маршрутизация.** Раз в `rerouteIntervalS` для навигаторных водителей: пересчёт по текущим временам проезда.
   Обычные водители держат маршрут, выбранный при появлении.
4. **Выбор полосы (намерение).** За `laneSelectionLookaheadM` до конца линка машина определяет целевую полосу
   по следующему манёвру маршрута (turns полосы) и правам доступа (выделенка, карман).
5. **Перестроения (MOBIL).** Для машин с намерением или с выигрышем по ускорению: критерий безопасности
   (торможение нового последователя ≤ b_safe) и стимул с вежливостью. Обязательные перестроения
   (поворот, конец полосы) получают растущий бонус по мере приближения к концу.
6. **Продольное ускорение (IDM)** относительно лидера, а также относительно «виртуальных препятствий»:
   стоп-линия при красном, точка конфликта при уступании, зебра с пешеходами, конец кармана при переполнении,
   стоящий автобус, заполненный выезд (gridlock-дисциплина), точка слияния. Каждое препятствие даёт своё
   ускорение; берётся минимальное, и его источник становится **связывающим ограничением** (`cause`).
7. **Интеграция.** `v += a·dt`, `s += v·dt` (полунеявный Эйлер), переходы полоса → коннектор → полоса.
8. **Появление и исчезновение.** Ворота и точки притяжения порождают машины по OD-таблице и профилю часа,
   с учётом бюджета; на воротах выхода машины удаляются, статистика поездки закрывается.
9. **Автобусы.** Расписание по интервалам, остановки: подъезд к `s` остановки, стоянка `busDwellS`
   (в полосе или в кармане), продолжение.
10. **Метрики.** Раз в `sampleIntervalS`: накопление по сегментам (скорость, плотность, поток, очередь,
    задержка, причины) в кольцевые окна; распространение корневых причин (см. ниже).
11. **Инварианты** (только `debugInvariants`): нет NaN, нет наложений, нет отрицательных зазоров.

## Светофоры
Контроллер: фазы по кругу, `offsetS` сдвигает начало цикла. Состояние группы в момент t:
- фаза, где группа зелёная: `GREEN`, последние `flashingGreenS` секунд `FLASHING_GREEN`, затем `YELLOW` фазы;
- перед своей зелёной фазой за `redYellowS` секунд: `RED_YELLOW`;
- иначе `RED` для основных секций и `OFF` для `arrow_*`.
Коннектор с `protection: protected` едет на зелёный без проверки конфликтов; `permissive` при зелёном
проверяет зазоры на точках конфликта против встречных `through`/`right`; `arrow_off`: левый коннектор при
основном зелёном и погашенной стрелке стоит (причина `arrow_off`).
Жёлтый: машина, которая не может остановиться комфортно, проезжает; остальные тормозят (простая дилемма-зона).

## Перекрёстки и конфликты
Компилятор строит коннекторы (полоса → полоса) и точки конфликта геометрически (пересечение полилиний),
назначая приоритет: сигнал, главная дорога (класс дороги), правило правой руки, для слияний — уступает съезд.
В рантайме уступающая машина ждёт, пока ни одна приоритетная не окажется в «зоне конфликта» ближе критического
зазора по времени (gap acceptance). **Gridlock:** перед въездом на коннектор проверяется, есть ли на выходной
полосе место длиной `length + s0`; водитель с вероятностью `gridlockDiscipline` ждёт, иначе въезжает и
может остановиться внутри перекрёстка, блокируя поперечные коннекторы (их причина `gridlock`).

## Карманы и выделенки
Карман: полоса с `startS > 0`; соседство слева/справа учитывает `startS/endS`. Левоповоротная машина, не
успевшая войти в карман (карман полон), останавливается в сквозной полосе с причиной `pocket_spillback`;
машины позади наследуют её как корневую причину. Выделенка: `allowed` без `car`; исключение для правого
поворота в последних `carsMayEnterForRightTurnWithinM`; нарушители (`BUS_LANE_VIOLATOR`) игнорируют запрет.
Вне часов действия полоса становится общей.

## Автобусы и пешеходы
Автобус движется по `linkIds` маршрута, на каждой остановке стоит `busDwellS` (×`busDwellPeakFactor` в пик);
`in_lane` — стоит в полосе (лидер для остальных, причина `behind_stopped_bus`), `bay` — исчезает из полосы
на время стоянки. Пешеходы: у зебры очередь ожидающих и «идущие» с позицией; поворачивающая машина
(`crosswalkIds`) уступает идущим, если её время прибытия к зебре меньше критического зазора.

## Причины и распространение корневой причины
Каждая машина хранит `cause` (немедленную). `rootCause` вычисляется на этапе метрик: если `cause == leader`
и лидер стоит или едет медленнее порога, `rootCause = rootCause(лидера)` (цепочка ограничена глубиной 200,
идёт от головы очереди назад за один проход по упорядоченному списку полосы). Через границу полоса → коннектор
→ полоса цепочка продолжается. Метрики сегментов накапливают задержку по `rootCause`, поэтому у очереди
перед переполненным карманом 100% задержки честно ложится на `pocket_spillback`, а не на «машину впереди».

## Метрики и детектор
Сегменты 25 м. Раз в секунду для сегмента: средняя скорость машин на нём, число машин, проход через конец,
длина стоящей части, задержка = Σ(dt·(1 − v/v_free)) по машинам, задержка в людях = ×наполненность класса
(пик/непик по часу). Скользящее окно `windowS` (кольцевой буфер по секундам). V/C: поток через конец сегмента
относительно ёмкости полосы (1800 веh/ч × доля зелёного, если сегмент подходит к светофору).
Детектор (`T-19`): кандидаты — подходы к узлам и середины линков, где `speedRatio < 0.3`, `congestedShare ≥ 0.6`,
`queueM ≥ 40`, а следующий по потоку сегмент имеет `speedRatio ≥ 0.5`. Ранжирование по `delayVehH` за окно
(переключаемо на человеко-часы). Объяснение: доли `rootCause` по сегментам подхода; рекомендации таблицей
«доминирующая причина → сценарий» с готовыми `overrides`.

## Воркер и буферы
`sim-worker` держит 2–3 `FrameBuffers`. Цикл: пока есть свободный буфер и пришло время кадра (`frameRateHz`),
`writeFrame` → `postMessage(frame, transfer)`; главный поток после рендера шлёт `returnFrame`. Скорость
воспроизведения `speedFactor`: воркер делает `floor(speedFactor·dt_wall/dtS)` шагов на итерацию, при
нехватке времени честно снижает и сообщает `rtFactor`. Метрики и отчёт — отдельные сообщения, JSON для отчёта
(маленький), typed arrays для метрик.

## Рендер
Полотно и разметка строятся из сети один раз (BufferGeometry по полосам: ширина, штрихи, сплошные, буква А
и цвет выделенки, стрелки в поворотных полосах, стоп-линии, зебры). Машины: `InstancedMesh` на класс, позиция
интерполируется между двумя последними кадрами по `id`. Светофоры: инстансы «ламп» с цветом по
`signalStates`. Тепловая карта: атрибут цвета на геометрии сегментов, обновляется из `MetricsFrame`.
Подписи и маркеры Топ-N: CSS2D. Здания/парки/реки: склеенные меши, слой с выключателем.

## Сценарии и A/B
Сценарий = `overrides` + `params`. Применение: `applyOverrides(network, overrides)` (детерминированно) → новый
`Network` → новый воркер с тем же сидом. Для A/B живут два клиента; UI переключает, какой из них рисуется,
панель сравнения считает дельты по двум последним отчётам и находит «новые узкие места» (id, которых нет в A).

## Производительность и бюджет
Целевая нагрузка: 20 000 машин при 10 шагах/с в реальном времени на M5 Max. Спавн ограничен бюджетом; при
`rtFactor < 0.8` в течение 10 с приложение предлагает снизить бюджет. Пространственные запросы только
через списки полос (нет глобального поиска соседей). Профилирование и оптимизации — T-27.

## Детерминизм
Один `Rng` на симуляцию, форки на подсистемы (спавн, водители, пешеходы, маршрутизация, автобусы).
Порядок обработки машин — по индексу слота, порядок полос — по индексу. `trajectoryHash` (FNV-1a по
округлённым x, y, v всех машин на каждом шаге) используется в регрессии и тесте N04.
