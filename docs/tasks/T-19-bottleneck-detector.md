# T-19. Детектор узких мест, объяснение, рекомендации

**Пакет:** `packages/sim-core` · **Волна:** 4 · **Уровень:** S · **Размер:** ~800 строк · **Зависит от:** T-18 · **Разблокирует:** T-20, T-25, T-26

## Цель
Реализовать `report()`: найти узкие места по трём условиям, ранжировать по задержке, собрать объяснение из долей
корневых причин и рекомендации с готовыми overrides. Закрывает N22, N23 и первую проверку N24.

## Контекст
`docs/ARCHITECTURE.md` («Метрики и детектор»); `packages/contracts/src/metrics.ts` (`BottleneckItem`, `Recommendation*`,
`losFromVc`); `docs/DECISIONS.md` D11; `describeApproach` из T-07 (в sim-core недоступен: сим-ядро получает имена узлов
из `Network.nodes[].name` и направления считает сам по геометрии подхода: запад/восток/север/юг по углу).

## Что сделать
1. **Кандидаты.** Группы сегментов: «подход» = последние `min(6, все)` сегменты полос одного линка перед узлом,
   агрегированные по полосам (взвешенно по числу машин); «середина линка» = остальные сегменты линка. Для каждой группы
   за окно: `speedRatio`, `congestedShare`, `queueM` (макс по полосам), `delayVehH/PersonH` (сумма), `vcRatio` (макс).
2. **Условия.** `speedRatio < speedRatioMax`, `congestedShare ≥ minPersistence`, `queueM ≥ minQueueM`, и следующий по потоку
   участок (сегменты линков-выходов через коннекторы с наибольшим потоком) имеет `speedRatio ≥ downstreamSpeedRatioMin`.
   Исключение: если выход ведёт на ворота (ничего дальше нет), условие «ниже свободнее» считается выполненным.
3. **Ранжирование** по `delayVehH` (переключатель на person в конфиге отчёта — параметр `report({by: "person"})`?
   Интерфейс `report()` без аргументов: считать оба, `rank` по машинам; UI пересортирует по людям сам).
4. **Объяснение.** `causes` = нормированные доли `causeShare` по группе, только `DELAY_CAUSE_KEYS`, топ-5.
   `title` = `${node.name}, подход с ${направление}` или `${link.name}, участок`. `focus` = координата стоп-линии.
   `id` стабильный: `${linkId}:${nodeId ?? "mid"}`.
5. **Рекомендации** таблицей «доминирующая причина → сценарий» с готовыми overrides:
   `gap_left_turn` → `add_left_arrow` (`signal.leftTurnModes[link] = protected`) и `prohibit_left_turn`;
   `pocket_spillback` → `extend_left_pocket` (+60 м) ; `signal_red` при V/C > 0.9 → `rebalance_green` (+10 с группе подхода);
   `arrow_off` → `rebalance_green` стрелке; `behind_stopped_bus` → `bus_stop_bay`; `pedestrian_yield` → `rebalance_green`;
   `gridlock` → `discipline_enforcement` (params `gridlockDiscipline: 1`, без overrides); `merge_yield` → `ramp_metering` (только label);
   `downstream_spillback` → `none` с подписью «причина ниже по потоку: см. #N» (ссылка на другой элемент отчёта);
   на выделенке с низкой загрузкой автобусов при `signal_red` → `bus_lane_hours`. Не более 3 рекомендаций.
6. `totals` из T-18; `items` до `topN`.
7. Тесты: N22 (`multiplier` 0.5 vs 1.5), N23 (сценарий выделенки: person-delay ниже при vehicle-delay выше — фикстура
   `straightRoad` с частыми автобусами и насыщением легковых), N24 первая проверка (`crossroads({leftPocketM: 40})` с высоким
   левым спросом → топ-1 подход с доминирующей `pocket_spillback`; `crossroads({leftPocketM: 0, permissive})` → `gap_left_turn`);
   стабильность `id` между двумя отчётами; рекомендации содержат валидные overrides (парсятся `NetworkOverrideSchema`).

## Заметки от T-18 (учесть)
- **Что даёт ядро.** `kernelOf(sim).segmentIndex` — `segLane`, `segIsApproach`, `segEndS`, `segCapacityVehH`,
  `firstSegmentOfLane`/`lastSegmentOfLane`, `connSegment`. «Следующий по потоку сегмент» — следующий индекс
  внутри полосы, а за концом полосы — `firstSegmentOfLane(connToLane[c])` её коннектора.
  `kernelOf(sim).metricsWindow` — сам накопитель окна: `stopsInWindow(segment)` (в `MetricsFrame` поля под
  остановки нет, контракты заморожены) и `vcRatio(segment)` мимо сворачивания кадра.
  Связки «сегмент → подход» в кадре нет — держите её у себя из `SegmentDescriptor.approachNodeId`.
- **`delayVehS` пилит на ±6% с периодом `windowS / 8`** (кольцо из 8 слотов вытесняется целиком; замер —
  раздел «Заметки после ревью» в карточке T-18). Ранжирование не страдает — множитель одинаков для всех
  сегментов, — но `minPersistence` и абсолютные пороги по задержке берите с запасом ≥ 12%.
- **V/C систематически занижен примерно на 10%.** В знаменателе справочные
  `signals.saturationFlowVehPerHPerLane` = 1800, а реальный эмерджентный saturation flow на дефолтных
  водительских параметрах — 1550–1650 (замер N05, заметка ревью T-09). `speedRatioMax`/`minPersistence`
  калибруйте по факту, а не от «должно достигать 1800».
- **`congestedShare` запечён порогом `bottleneck.speedRatioMax` на этапе накопления** — менять порог без
  перезапуска нельзя. Если нужен подбор на лету, это отдельная правка `MetricsAccumulators`.
- **N10 стоит переписать на подход.** Ожидание «доминирующая причина `gap_left_turn` на подходе» теперь
  выполнимо по корневым причинам (`causeShare` на сегментах подхода); текущий тест всё ещё проверяет
  доминирование на самом коннекторе.
- **Вторая проверка N09** («доля `pocket_spillback` на подходе > 20%», `it.todo` в `03-turns.test.ts`)
  технически проходит уже сейчас — замер на её фикстуре даёт ~0,88. Нюанс числится за T-10/T-22, todo не трогали.

**Реальный дефект уровня карточки (не реализации): порог `V/C > 0.9` глушит `rebalance_green`.**
Правило §5 «`signal_red` при V/C > 0,9 → `rebalance_green`» на реальной сети не срабатывает практически
никогда, потому что `vcRatio` считается по **реализованному** потоку: чем сильнее заперт подход, тем
меньше через него проезжает и тем ниже V/C. Замер на топ-6 `almaty-abay-small`: #3 `signal_red` 0.35 при
V/C **0.38**, #4 `signal_red` 0.40 при V/C **0.08**, #6 `signal_red` 0.62 при V/C **0.41** — у всех трёх
узел регулируемый и группа `main` для этого линка в плане есть (проверено по `net.signalControllers`),
то есть единственное, что отсекает рекомендацию, — порог `REBALANCE_MIN_VC`. В итоге из топ-6 реальной
сети рекомендацию получают два элемента. Исполнитель реализовал ровно то, что написано в карточке,
поэтому на `main` порог **не менялся**: это решение владельца. Варианты — считать порог по спросу
(поток на входе группы, а не на выходе), либо снизить `REBALANCE_MIN_VC` до уровня, отражающего
занижение V/C на ~10 % из заметок T-18, либо убрать гейт и полагаться на доминирующую причину.

**«LOS A при очереди 137 м» — то же самое, подтверждено.** `los = losFromVc(vcRatio)` из карточки и
контракта, а `vcRatio` реализованный: на `almaty-abay-small` элемент #1 отчитывается `queueM` 95 м,
`speedRatio` 0.00, `persistence` 1.00 — и `los` **A**; #4 — 133 м, `speedRatio` 0.00, `los` **A**.
Это не баг реализации, но в панели T-25 показывать `los` в одиночку нельзя (см. заметку в карточке T-25).

**Часть узких мест принципиально остаётся без рекомендаций, и это нормально.** Элемент #2 реальной сети —
доминирующая причина `pedestrian_yield` 0.99 на узле, у которого **вообще нет светофора**
(`signalControllers` покрывают 70 узлов из 444), а единственный сценарий для этой причины —
`rebalance_green`. Панель T-25 обязана уметь рисовать элемент с пустым `recommendations`.
