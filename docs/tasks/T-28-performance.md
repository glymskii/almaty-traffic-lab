# T-28. Производительность

**Пакет:** `packages/sim-core`, `packages/sim-worker` · **Волна:** 6 · **Уровень:** S · **Размер:** ~600 строк · **Зависит от:** T-22 · **Разблокирует:** T-29

## Цель
20 000 машин при 10 шагах/с в реальном времени на M5 Max (средний шаг ≤ 30 мс с запасом), автоснижение бюджета
на слабых машинах, бенчмарк в CI как мягкий порог. Закрывает N27.

## Что сделать
1. Бенчмарк-гарнитура: `pnpm sim --bench` на большом полигоне (если сеть есть) и на синтетическом `corridor({intersections: 40})`;
   профиль через `node --cpu-prof`; таблица «до/после» в отчёте.
2. Типовые оптимизации: отсутствие аллокаций в шаге, замена `Map`/объектов на typed arrays, кэш соседей полос,
   инкрементальное обновление списков полос, дешёвая проверка конфликтов только для машин в 50 м от узла, метрики
   с шагом семпла 1 с без пересчёта по всем машинам чаще, чем нужно, маршрутные деревья без пересборки, если стоимости
   не изменились.
3. Воркер: `maxStepsPerIteration` адаптивно; при `rtFactor < 0.8` 10 с подряд — событие для UI; кнопка «снизить бюджет»
   меняет `demand.vehicleBudget`? Это не runtime-safe: реализовать как перезапуск с сохранением сценария (UI T-23).
4. N27 как тест с `describe.skipIf(!process.env.ATL_BENCH)`; GitHub Actions job `bench` (T-30) с мягким порогом.

## Критерии приёмки
- [ ] Отчёт с числами до/после; N27 проходит локально; `pnpm check` зелёный; детерминизм не нарушен (регрессия T-20).

## Заметки от T-04 (учесть)
- `repairOrder` обходит все треки каждый шаг; для большого полигона помечать только треки с двумя и более машинами.
